## 0. 核心结论

餐饮 SaaS 的增长规律，不是简单的：

```text
用户越多 -> 数据越多 -> 模型越强 -> 销售越好
```

而应该是：

```text
同类餐厅越多
  -> 同类问题越清楚
  -> 同类干预动作越可复用
  -> 同类 ROI 越可证明
  -> 销售越容易
  -> 交付越快
  -> 留存越高
  -> 更多同类餐厅加入
```

所以真正的 scaling law 不是“原始数据量”的增长，而是“可验证经营证据密度”的增长。

最核心的数据资产是这个六元组：

```text
restaurant_segment
+ problem_type
+ action_type
+ measured_outcome
+ guardrail_result
+ merchant_adoption
```

通俗讲，就是系统要持续积累：

> 什么类型的餐厅，遇到了什么问题，采取了什么动作，带来了什么结果，有没有副作用，老板是否真的采纳。

这组数据越多，SaaS 越能证明自己有用，越能快速成交、快速交付、快速复用成功经验。

# 1. SaaS 企业到底在卖什么？

餐饮老板买 SaaS，表面上买的是软件，实际上买的是确定性。

老板最关心的问题通常是：

```text
用了以后能不能多赚钱？
多久能看到效果？
会不会增加员工负担？
会不会搞乱菜单？
会不会影响出餐？
会不会乱发券、乱改价？
我的店和你的成功案例像不像？
出了问题能不能撤回？
```

所以 SaaS 的销售数据，不只是为了训练模型，更是为了降低客户的三类不确定性。

## 1.1 降低收益不确定性

老板怕的是：

```text
买了没效果。
```

因此 SaaS 需要证明：

```text
同类门店用了以后，支付转化提升了多少，加购率提升了多少，客单价提升了多少，等待时间有没有恶化。
```

## 1.2 降低交付不确定性

老板怕的是：

```text
接入麻烦，员工不会用，最后没人管。
```

因此 SaaS 需要证明：

```text
类似门店平均几天接入，几天出第一份报告，几天产生第一个有效动作。
```

## 1.3 降低风险不确定性

老板怕的是：

```text
系统乱改菜单、乱发券、影响老客、拖慢后厨。
```

因此 SaaS 需要证明：

```text
每个动作有依据、有确认、有回滚、有复盘，且等待时间、退款、差评等 guardrail 没有恶化。
```

结论：

> 对 SaaS 销售最有价值的数据，不是“用户点了什么”，而是“我曾经帮和你类似的餐厅，解决过和你类似的问题，并且结果可验证”。

# 2. 哪些数据最有助于 SaaS 本身销售？

## 2.1 ROI 证据数据

这是最直接帮助成交的数据。

需要记录：

```text
干预前指标
干预后指标
对照窗口
动作类型
影响菜品
影响时段
样本量
置信度
副作用指标
```

示例：

```text
门店类型：写字楼快餐简餐
问题：午高峰支付放弃率高
动作：降低复杂菜曝光，提升快出套餐
结果：
- 支付放弃率从 13.2% 降到 9.8%
- 平均等待时间从 18 分钟降到 14 分钟
- 客单价从 37.8 元变成 37.2 元
- 差评率无明显上升
- 7 天内多产生约 4,200 元 GMV
```

价值：

- 销售案例
- ROI calculator
- 续费材料
- 涨价依据
- 客户成功复盘
- 行业白皮书

## 2.2 相似餐厅 Benchmark 数据

餐饮老板最容易被打动的不是“行业平均”，而是：

```text
和我差不多的店，比我做得怎么样？
```

需要记录餐厅画像：

```text
品类
城市
商圈类型
门店面积
桌台数
日订单量
客单价区间
堂食 / 外带 / 外卖比例
午高峰 / 晚高峰结构
菜单 SKU 数量
员工数
厨房复杂度
会员占比
小程序点餐占比
```

示例销售表达：

```text
同城同品类同客单价门店中：
你的支付放弃率高于 73% 的门店；
你的加购率低于同类门店中位数 4.8 个百分点；
你的午高峰等待时间比同类门店长 6 分钟。
```

价值：

- 制造认知冲击
- 让客户知道差距在哪里
- 让产品从“可有可无”变成“必须优化”

## 2.3 可复用 Playbook 数据

SaaS 规模化销售的关键，是把“每家店重新咨询”变成“同类问题复用同类动作”。

需要沉淀：

```text
某类餐厅 + 某类问题 + 某类动作 = 大概率有效
```

示例：

| 餐厅类型 | 常见问题 | 高胜率动作 |
|---|---|---|
| 写字楼快餐 | 午高峰支付放弃高 | 快出套餐前置、复杂菜降曝光 |
| 茶饮店 | 加购率低 | 小料推荐、第二杯优惠、套餐组合 |
| 咖啡店 | 早餐客单低 | 咖啡 + 烘焙组合、复购券 |
| 烘焙店 | 临期库存损耗 | 下午库存促销、组合包 |
| 轻食店 | 新客转化弱 | 招牌低风险组合、热量标签优化 |

价值：

- 销售话术更具体
- demo 更贴近客户
- 交付更标准化
- 客户成功更容易复制

## 2.4 Time-to-Value 数据

餐饮老板通常没有耐心等几个月。

需要记录：

```text
TTV-1: 从签约到第一个事件
TTV-2: 从接入到第一份报告
TTV-3: 从报告到第一个洞察
TTV-4: 从洞察到第一个动作
TTV-5: 从动作到第一个效果复盘
```

商业目标：

```text
Day 1 接入
Day 2 出菜单漏斗
Day 3 给出第一个建议
Day 7 复盘第一个动作
Day 14 形成 ROI 摘要
```

价值：

- 缩短销售周期
- 降低试用流失
- 提升续费概率
- 让销售可以承诺“7–14 天看第一轮证据”

## 2.5 产品使用行为数据

SaaS 自己要知道客户有没有真正进入价值闭环。

需要记录：

```text
老板是否每天打开日报
是否点击证据
是否接受建议
是否应用动作
是否追问
是否查看效果复盘
是否邀请店长/运营一起使用
是否配置自动规则
```

高留存信号：

```text
每周打开经营日报 >= 3 次
30 天内应用 >= 2 个建议
至少查看过一次效果复盘
主动问过“这个调整有没有用”
添加了店长/运营角色
```

流失风险信号：

```text
接入后 7 天没有打开日报
连续 3 次建议被忽略
没有完成第一个 action review
报告只展示问题，没有给出可执行动作
```

价值：

- 判断续费概率
- 判断扩店机会
- 触发客户成功介入
- 识别适合做案例的客户

## 2.6 SaaS 自己的销售漏斗数据

需要记录：

```text
线索来源
行业
城市
门店数
日单量
客单价
当前 POS / 小程序系统
是否连锁
是否有会员体系
是否有外卖
是否有 KDS
老板最关心的问题
demo 中最感兴趣的模块
试用期是否产生第一个 action
成交周期
成交价格
续费情况
```

价值：

- 找到最强 ICP
- 判断哪些客户不该卖
- 判断哪个渠道 LTV/CAC 最好
- 优化 demo 和销售话术

## 2.7 集成与交付成本数据

很多 SaaS 不是死在卖不出去，而是死在交付太重。

需要记录：

```text
接入哪个 POS 最快
哪个小程序框架最容易接
哪个客户的数据最脏
哪个品类需要最多配置
哪个功能客服解释成本最高
哪些事件经常缺失
哪些菜单结构最难建模
哪些动作最容易出错
```

价值：

- 决定先支持哪个 POS / 小程序生态
- 决定先打哪个餐饮品类
- 决定哪些客户暂时不卖
- 决定哪些服务要产品化

## 2.8 信任与安全数据

餐饮老板最怕系统“乱动”。

需要记录：

```text
每次建议的证据
每次动作的前后变化
谁点击了应用
改了哪些菜单项
什么时候改的
能不能回滚
回滚后结果如何
有没有影响等待时间
有没有影响差评
有没有影响退款
```

价值：

- 降低购买恐惧
- 建立可审计信任
- 支持企业客户合规要求
- 避免 AI 黑盒印象

# 3. 六个核心指标：通俗解释、商业价值、怎么收集

这六个指标是 `data-dyna` 最关键的数据资产结构。

```text
restaurant_segment
+ problem_type
+ action_type
+ measured_outcome
+ guardrail_result
+ merchant_adoption
```

它不是普通报表字段，而是 SaaS scaling law 的最小证据单元。

## 3.1 restaurant_segment：这是什么类型的餐厅？

### 通俗解释

`restaurant_segment` 就是给餐厅画像，判断“这家店像哪类店”。

不要只写“餐饮店”，要尽量具体。

示例：

```text
写字楼快餐简餐
社区早餐店
商场茶饮店
学校周边炸鸡店
社区烘焙店
轻食沙拉店
小型连锁咖啡店
```

更完整的 segment 可以包括：

```text
品类 + 商圈 + 客单价 + 日单量 + 点餐方式 + 高峰结构
```

例如：

```text
写字楼 / 快餐简餐 / 客单价 25–45 / 日单 300–800 / 小程序点餐占比高 / 午高峰明显
```

### 1. 什么价值

它的价值是回答：

```text
这个客户和哪些成功案例相似？
我们能不能用已有经验快速说服他？
他适合用哪套 playbook？
他是不是当前阶段应该优先卖的 ICP？
```

没有 `restaurant_segment`，数据会混在一起。

火锅店、茶饮店、快餐店、烘焙店的问题完全不同。混在一起看平均值，会误导产品和销售。

对销售的直接价值：

```text
你这种类型的店，我们已经服务过 X 家，常见问题是 A/B/C，最有效动作通常是 D/E/F。
```

对产品的直接价值：

```text
优先为最强 segment 做功能，而不是为所有餐饮店做泛化功能。
```

### 2. 怎么收集

来源一：商户注册 / onboarding 表单。

建议字段：

```text
主营品类
门店数量
城市 / 商圈类型
客单价区间
日均订单量
堂食 / 外带 / 外卖比例
主要点餐方式
菜单 SKU 数
是否有会员体系
是否有 KDS / 后厨屏
是否有明显午高峰 / 晚高峰
```

来源二：系统自动计算。

例如：

```text
从订单时间分布识别午高峰强弱
从订单金额识别客单价区间
从菜单数量识别 SKU 复杂度
从支付渠道识别小程序点餐占比
从订单结构识别单人餐 / 多人餐 / 饮品加购特征
```

来源三：销售 / 客户成功标注。

例如：

```text
老板主要诉求：多卖 / 少等 / 少浪费 / 提高复购
门店经营阶段：新店 / 稳定店 / 扩张店 / 下滑店
数字化能力：弱 / 中 / 强
```

建议产品上做成：

```text
自动推断 + 人工确认
```

不要完全依赖老板填写，因为很多老板填不准；也不要完全依赖算法，因为早期数据不足。

## 3.2 problem_type：这家店遇到什么问题？

### 通俗解释

`problem_type` 是把老板的模糊问题变成可分析的问题类型。

老板可能会说：

```text
最近生意不好。
中午人很多但钱没多赚。
奶茶加料卖不动。
老客不来了。
差评变多了。
后厨忙不过来。
```

系统要翻译成：

```text
支付放弃率升高
点击率低
加购率低
客单价下降
复购周期变长
等待时间过长
退款率上升
差评率上升
库存损耗高
新品转化低
```

### 1. 什么价值

它的价值是把销售、产品和模型对齐到同一个问题语言。

对销售：

```text
客户不是买“AI”，而是买“解决午高峰支付放弃高”。
```

对产品：

```text
不同问题需要不同功能。
加购率低需要推荐/套餐；等待时间长需要履约和菜单曝光控制；复购差需要会员运营。
```

对数据飞轮：

```text
只有问题类型清楚，才能统计哪类问题最常见、最值钱、最容易解决。
```

### 2. 怎么收集

来源一：指标自动诊断。

示例规则：

```text
曝光很多但点击低 -> item_ctr_low
点击高但加购低 -> click_to_cart_low
加购高但支付低 -> checkout_abandonment_high
等待时间上升且差评上升 -> fulfillment_delay_problem
老会员下单间隔变长 -> retention_risk
库存剩余高且临期 -> inventory_waste_risk
```

来源二：老板 / 店长对话。

在 Assistant 中收集：

```text
“你最想解决什么？”
“最近最头疼的是多卖、少等、少浪费，还是复购？”
“这条诊断是否符合你的感受？”
```

来源三：销售 CRM。

销售第一次沟通时记录：

```text
客户主动提到的痛点
客户最关心的指标
客户愿意为哪个问题付费
```

来源四：客服 / 客户成功工单。

记录客户持续反馈的问题，例如：

```text
日报看不懂
建议不敢用
加购推荐没效果
活动复盘不清楚
```

建议把 `problem_type` 做成标准枚举，同时允许补充文字。

## 3.3 action_type：采取了什么经营动作？

### 通俗解释

`action_type` 是系统或商户为解决问题采取的动作。

不是“给了一个建议”就结束，而是要记录具体改了什么。

示例：

```text
调整菜单排序
提升快出套餐曝光
降低复杂菜曝光
设置加购推荐
生成优惠券草稿
发送复购提醒
隐藏售罄菜品
修改菜品图片
修改菜品名称
设置新品 Banner
设置高峰期菜单规则
发送等待安抚消息
```

### 1. 什么价值

它的价值是回答：

```text
到底什么动作有用？
哪些动作容易被老板接受？
哪些动作有副作用？
哪些动作可以产品化、自动化、标准化？
```

对销售：

```text
我们不是只给报表，而是有一套已经验证过的动作库。
```

对 SaaS 交付：

```text
把动作标准化后，客户成功不需要每家店重新咨询。
```

对未来自动化：

```text
只有 action_type 标准化，系统才能逐步从建议升级到半自动执行。
```

### 2. 怎么收集

来源一：Assistant action card。

每个建议都必须结构化为 action card：

```text
action_id
action_type
目标问题
影响菜品
影响时段
预期指标
风险指标
是否需要确认
是否支持回滚
```

来源二：后台配置变更日志。

例如：

```text
菜单排序从 A 改为 B
菜品 X 从首页第 3 位改为第 8 位
套餐 Y 在 12:00–13:00 提升曝光
优惠券 Z 被创建但未发送
```

来源三：商户手动动作。

即使老板没有通过系统执行，而是自己改了菜单，也应该允许记录：

```text
我已经线下改了图片
我自己把套餐放到了首页
我没有发券，只改了菜名
```

来源四：实验系统。

如果做 A/B 或 before/after，需要绑定：

```text
experiment_id
variant_id
action_id
exposure_id
```

建议产品规则：

> 每一个建议，如果无法落到明确 `action_type`，就不应该算作核心建议，只能算一般解释。

## 3.4 measured_outcome：动作之后结果怎么样？

### 通俗解释

`measured_outcome` 是动作带来的业务结果。

它回答：

```text
改完之后，到底有没有变好？
```

示例：

```text
支付放弃率下降 3 个百分点
加购率提升 5 个百分点
客单价提升 2.8 元
午高峰等待时间下降 4 分钟
复购周期缩短 2 天
退款率下降
GMV 增加
毛利增加
```

### 1. 什么价值

这是 SaaS 销售最强的数据。

如果没有 `measured_outcome`，销售只能说：

```text
我们能帮你分析。
```

有了它，销售可以说：

```text
同类门店用了这个动作后，14 天内支付放弃率平均下降 2–4 个百分点。
```

它也是续费、涨价和客户成功的基础。

对内部产品也非常重要：

```text
哪些功能真的带来价值？
哪些建议只是看起来聪明？
哪些动作值得优先做自动化？
```

### 2. 怎么收集

来源一：前后对比。

最简单方式：

```text
动作前 7 天 vs 动作后 7 天
上周同日 vs 本周同日
同一时段 before/after
```

来源二：A/B 测试。

如果流量足够：

```text
一部分用户看到菜单排序 A
一部分用户看到菜单排序 B
比较点击、加购、支付、客单价、等待和退款
```

来源三：时间窗口 holdout。

例如：

```text
只在 12:00–12:40 应用动作
对比 11:20–12:00 或历史同类午高峰
```

来源四：订单和行为事件自动计算。

需要事件能串起来：

```text
recommendation_exposed
recommendation_clicked
add_to_cart
checkout_start
payment_success
order_completed
refund
review
```

关键要求：

```text
action_id 必须能关联到后续指标变化。
```

否则无法证明结果来自哪个动作。

建议所有 outcome 都带上：

```text
baseline_window
measurement_window
sample_size
confidence_level
metric_delta
absolute_value_before
after_value_after
```

---

## 3.5 guardrail_result：有没有副作用？

### 通俗解释

`guardrail_result` 是安全指标，回答：

```text
虽然主指标变好了，但有没有伤害别的东西？
```

例如：

```text
加购率提升了，但等待时间是否变长？
客单价提升了，但退款率是否上升？
支付转化提升了，但差评是否变多？
复杂菜曝光降低了，但招牌菜销量是否受损？
优惠券带来订单了，但毛利是否被吃掉？
```

### 1. 什么价值

这是建立信任的核心。

餐饮老板最怕：

```text
系统为了一个指标好看，把门店搞乱。
```

所以销售必须能说：

```text
我们不只看 GMV，也看等待、退款、差评、毛利和履约压力。
```

对产品也重要：

```text
没有 guardrail，系统会鼓励短期转化，长期伤害体验。
```

对合规和品牌也重要：

```text
避免走向黑盒动态宰客、过度促销、损害消费者体验。
```

### 2. 怎么收集

按动作类型绑定 guardrail。

示例：

| action_type | 主指标 | guardrail |
|---|---|---|
| 菜单排序调整 | 点击率、加购率、支付率 | 等待时间、差评率、退款率、招牌菜销量 |
| 加购推荐 | 加购率、客单价 | 支付放弃率、退款率、等待时间 |
| 优惠券 | 下单率、复购率 | 毛利、补贴成本、原本会购买用户占比 |
| 隐藏复杂菜 | 等待时间、支付率 | 客单价、用户满意度、招牌菜曝光 |
| 新品推荐 | 新品转化 | 退款率、差评率、老品销量冲击 |

数据来源：

```text
订单完成时间
KDS / 后厨状态
退款记录
评价记录
客服投诉
毛利 / 成本数据
菜品销量结构
优惠券成本
```

建议产品规则：

> 每个 action card 必须声明至少一个主指标和至少一个 guardrail；如果 guardrail 数据缺失，必须明确提示“不足以判断副作用”。

## 3.6 merchant_adoption：老板有没有真的用？

### 通俗解释

`merchant_adoption` 是商户采纳度，回答：

```text
老板是否相信这个建议？
是否真的点了应用？
是否继续使用？
是否愿意为它付费？
```

示例：

```text
看了建议但没点
点击了查看依据
接受了建议
生成了草稿
应用了动作
应用后没有回滚
查看了效果复盘
继续追问
邀请店长一起看
升级了套餐
续费了
推荐给其他门店
```

### 1. 什么价值

这是判断 SaaS 是否真正被客户接受的核心。

有些建议指标上可能有效，但老板不敢用；有些功能看起来高级，但没人点。

`merchant_adoption` 可以回答：

```text
哪些建议老板愿意采纳？
哪些动作需要更强解释？
哪些功能是销售卖点但不是使用价值？
哪些客户会续费？
哪些客户有流失风险？
```

对销售：

```text
高采纳率说明产品不是摆设，而是经营流程的一部分。
```

对客户成功：

```text
低采纳但高潜力客户需要介入培训；低打开低采纳客户可能要流失。
```

对产品：

```text
优先做老板愿意用、且结果有效的动作。
```

### 2. 怎么收集

来源一：产品行为事件。

需要记录：

```text
daily_report_opened
evidence_viewed
action_card_viewed
action_card_accepted
action_card_rejected
action_card_applied
action_card_reverted
effect_review_viewed
followup_question_asked
team_member_invited
```

来源二：对话反馈。

Assistant 可以问：

```text
这个建议你觉得可执行吗？
你为什么不想应用？
是否要记住“不要隐藏招牌菜”这个偏好？
这次效果是否符合你的实际感受？
```

来源三：商业行为。

例如：

```text
试用转正
续费
升级套餐
扩展到更多门店
主动索要周报/月报
推荐其他商户
```

来源四：客户成功记录。

例如：

```text
培训完成
老板认可
店长反对
员工不会操作
觉得建议太复杂
需要人工陪跑
```

建议将 adoption 拆成几个层级：

```text
saw: 看到了
understood: 看懂了
trusted: 看了依据并认可
accepted: 接受建议
applied: 应用动作
reviewed: 看了复盘
repeated: 再次使用同类动作
paid: 为能力付费或续费
```

这比单纯统计“点击率”更有商业意义。

# 4. 六元组如何形成 scaling law

六元组的关键不是单点记录，而是长期积累后形成可复用知识。

单条记录长这样：

```text
restaurant_segment:
  写字楼快餐简餐 / 客单价 25–45 / 日单 300–800 / 午高峰明显
problem_type:
  午高峰支付放弃率高
action_type:
  快出套餐前置 + 复杂菜降曝光
measured_outcome:
  支付放弃率下降 3.4pp，等待时间下降 4 分钟，GMV 提升 6.8%
guardrail_result:
  客单价下降 0.6%，差评无明显上升，退款无明显上升
merchant_adoption:
  老板采纳，连续使用 7 天，查看复盘后选择继续
```

当这种记录越来越多，系统就能回答：

```text
哪类餐厅最适合卖？
哪类问题最普遍？
哪类动作胜率最高？
哪类动作副作用最大？
哪类建议老板最愿意采纳？
哪类客户最容易续费和扩店？
```

这会推动完整飞轮：

```text
更多同类餐厅
  -> 更多相似问题记录
  -> 更多 action -> outcome 证据
  -> 更强 benchmark 和 playbook
  -> 更有说服力的销售材料
  -> 更快成交
  -> 更低交付成本
  -> 更高采纳和续费
  -> 更多同类餐厅
```

# 6. 商业建议

## 6.1 早期不要追求客户数量，追求同类证据密度

错误目标：

```text
半年拿下 500 家各种餐厅。
```

更好的目标：

```text
半年拿下 80–150 家高度相似的目标餐厅，
在其中跑出 30–50 个可复用 action -> outcome 案例。
```

这样产品、模型、销售、交付都会更快形成飞轮。

## 6.2 不要卖 AI，卖 7–14 天内看到经营证据

更好的销售表达：

```text
我们用 14 天帮你找出菜单收入泄漏点，并验证至少一个可执行优化动作。
```

餐饮老板不一定相信“大模型”，但会理解：

```text
每天多 20 单，每单多 3 元，一个月是多少。
```

## 6.3 每个 action card 都要天然沉淀为销售资产

每个建议都应该记录：

```text
客户类型
问题类型
建议动作
是否采纳
采纳后效果
副作用
客户反馈
是否可复用
```

产品使用过程应该自动生成未来的销售案例。

## 6.4 建立餐饮经营动作库

长期壁垒不是 UI，也不是普通报表，而是：

```text
在什么场景下，什么动作，大概率有效。
```

例如：

```text
写字楼快餐：
午高峰等待 > 16 分钟且支付放弃率上升时，
降低复杂菜曝光 + 提升快出套餐，
通常比直接发券更有效。
```

## 6.5 把客户成功变成产品的一部分

系统要自动回答：

```text
这个客户有没有获得价值？
有没有进入闭环？
有没有使用建议？
有没有查看复盘？
有没有扩店机会？
有没有流失风险？
```

这样 SaaS 自己也拥有一套 operating system。

# 7. 最终定义

餐饮 SaaS 的 scaling law 可以定义为：

> 餐饮 SaaS 的能力随“同类餐厅场景中，可验证、可复用、可销售的经营动作证据”增长，而不是随原始数据量增长。

更短：

```text
更多同类餐厅
  -> 更多相似问题
  -> 更多被验证动作
  -> 更强 benchmark
  -> 更快成交
  -> 更快交付
  -> 更高留存
  -> 更多同类餐厅
```

因此，`data-dyna` 最核心的数据资产不是点击流本身，而是：

```text
restaurant_segment
+ problem_type
+ action_type
+ measured_outcome
+ guardrail_result
+ merchant_adoption
```

如果从第一天就围绕这个六元组设计产品、数据、销售和客户成功，它会成为真正的餐饮 SaaS scaling law。
